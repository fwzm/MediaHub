# G6 · M14 残余风险收口：并发 Range 互斥与 stop() 同步契约（V12 24h 作业）

**run_id**: 20261017T220451-mediahub-v12 | **分支**: feature/g6-m14-residual-closure
**基线 head**: 9c7ac6ec177ebc43510805f935df3c91da3cb765

## 1. 先如实说明这条切片**不是什么**

本轮**没有**修复并发 Range 缺陷 —— 因为生产代码**本来就是正确的**（`synchronized(handle)` 包住整段 seek+read）。
本切片做的是**把既有契约钉死**，防止未来有人「优化」掉那把锁。

按 V12 §10.2 的要求，这里明确标注：**BASELINE_PASS（补充守护），不是 RED→GREEN 修复**。

## 2. 为什么值得补（既有覆盖的缺口）

`MpvHttpBridgeHandleLifecycleTest`（8 例）已覆盖：会话内只打开一次句柄、stop 恰好关闭一次、
声明长度=实际字节（W2 已消除）、stop 与在途传输并发时 fd 仍释放。

但那里**没有**覆盖：**多个并发 Range 在同一会话句柄上 seek+read 是否互相破坏**。
句柄是会话级共享的，`seek(start)` 与后续 `read` 之间存在天然竞态；
生产代码用 `synchronized(handle)` 保护整段传输，此前没有任何测试守护这一点。

## 3. 新增测试（3 例，全绿）

`core/network/src/test/kotlin/com/mediahub/core/network/MpvHttpBridgeConcurrentRangeTest.kt`

| 用例 | 断言 |

| `concurrent distinct range requests on one session handle each get their own exact slice` | 4 个互不重叠区间（0-262143 / 1048576-1310719 / 2097152-2359295 / 3145728-4194303）并发请求；每段必须**逐字节**正确；句柄只打开一次 |

## 4. 变异验证（关键：证明测试不是空断言）

```
PASS: concurrent range requests never violate the declared content length
```

**测试确实抓到了变异**（读到错位字节，首字节 0 变成 -60）。随后 `git checkout` 恢复源码，
再次运行 3/3 全绿。

这说明：
- 该测试**有效**（不是恒真断言）；
- 生产代码的互斥**是必需的**（删掉就会读到错位数据）；
- 但生产代码**当前是对的** → 本切片定位为「守护」而非「修复」。

## 5. W1 维持 UNPROVABLE（V12 §06 明确要求）

`isFile/canRead` 与首次 `open` 之间的 check-then-open 窗口（W1）**仍未消除**：
