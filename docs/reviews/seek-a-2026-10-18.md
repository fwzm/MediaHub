# SEEK-A · 消灭「测试绿但没测到真实代码」（V13 作业）

**分支**: `feature/seek-a-real-component-test` | **基线**: `726177e435dadd0d1f8537e0ea6956c24ca7b89f`

## 1. 问题（V13 §03 事实确认）

PR #53 的 4 个 Compose Seek 测试构造的是**测试自有的 Slider 副本**：

```kotlin
composeRule.setContent {
    Slider(modifier = Modifier.testTag(...),
           onValueChange = { scrub = it; recorder.previews += it },   // ← 测试自己的回调
           onValueChangeFinished = { recorder.commits += ... })
}
```

把生产 `onValueChange` 改成「变更即提交」后，它们**仍然 4/0 全绿**（变异存活）。
因此这 4 例只能证明 Compose 框架的 Slider 语义，**不能认证真实 PlayerControls**。

## 2. 修法：抽取生产组件 `PlayerSeekBar`（V13 §03.6 允许的路径）

`PlayerControls` 是 `private` 且依赖 20+ 参数，直接实例化成本过高。按 §03.6「可只抽取
没有业务复制的新组件 PlayerSeekBar，并让生产 PlayerControls 真实引用它」：

- 新增 `internal fun PlayerSeekBar(positionMs, durationMs, onSeek, colors, modifier)`
  于 `PlayerScreen.kt`，**行为与原内联 Slider 逐字节等价**（同一参数、同一 preview→commit 顺序）；
- `PlayerControls` 内的两处内联 `Slider` 改为调用它 → **生产代码真实引用**，
  不是「同名测试组件代替生产代码」；
- `PlayerVisualTestTags` 新增 `PLAYER_PROGRESS`（仅语义标识，行为不变）。

## 3. 测试：用**真实触摸**而非语义动作

关键决策：**不用** `SemanticsActions.SetProgress`。该语义动作在 Robolectric 下会
连带触发 `onValueChangeFinished`（PR #53 也遇到过），那样永远测不出「拖动中不提交」。
改用 `performTouchInput { swipe(...) }` —— 这才是用户的真实手势：拖动中多次
`onValueChange`，松手时一次 `onValueChangeFinished`。

`PlayerSeekBarContractTest`（4 例）：

| 用例 | 断言 |
|---|---|
| `progress bar is discoverable by stable tag` | 生产组件可按 `PLAYER_PROGRESS` 定位 |
| `a real drag commits exactly once at release` | 真实 swipe（10%→50%）全程 **onSeek 恰好 1 次**，目标落在 38–52s |
| `no further commits after the drag ends` | 拖动结束后**不得再有**提交 |
| `unknown duration disables the bar and never commits` | `durationMs=0` 时禁用且 0 次提交 |

## 4. 变异验证（本切片的核心价值）

### MUT-1：把生产 `onValueChange` 改为「变更即提交」

```kotlin
onValueChange = { sliderScrubValue = it; onSeek(it.roundToLong()) },  // MUT-1
```

结果 **BUILD FAILED**（4 tests / 2 failed）：

```
FAIL: a real drag commits exactly once at release
  java.lang.AssertionError: 一次真实拖动必须只提交一次（拖动中是预览，不提交）；
  实际=[7777, 10064, 12117, 14170, 16223, 18147, 20200, 22253, 24306, 26230,
        28283, 30336, 32389, 34442, 36366, 38419, 40472, 40472] expected:<1> but was:<18>
FAIL: no further commits after the drag ends
  java.lang.AssertionError: 并且恰好是一次 expected:<1> but was:<19>
```

**注意 18 个递增位置（7777→40472）**——这直接证明测试贯穿了真实组件的拖动采样，
不是空断言。

### MUT-2：移除 `onValueChangeFinished` 的提交

结果 **BUILD FAILED**（4 tests / 2 failed）：

```
FAIL: a real drag commits exactly once at release
  java.lang.AssertionError: 一次真实拖动必须只提交一次；实际=[] expected:<1> but was:<0>
FAIL: no further commits after the drag ends
  java.lang.AssertionError: 并且恰好是一次 expected:<1> but was:<0>
```

### 恢复后 GREEN

```
GREEN: tests=4 failures=0
  - no further commits after the drag ends (7.068s)
  - progress bar is discoverable by stable tag (0.165s)
  - unknown duration disables the bar and never commits (0.143s)
  - a real drag commits exactly once at release (0.207s)
```

**结论**：两个变异都成功杀死测试 → 这 4 例真正覆盖了生产 `PlayerSeekBar` 的
preview→commit 分离，而不是框架行为。**SEEK-UI 门禁达成**（V13 §11）。

## 5. 边界（不越界声明）

- 本切片只证明 **UI 层**「拖动不提交 / 松手提交一次 / 目标正确」；
- **不证明**引擎真的把播放位置移到了该处 —— 那必须由 **SEEK-B 真机实测**独立验证；
- 因此 Seek **仍不能**从 `NOT_RUN` 升格为 PASS；当前最多是 `SEEK-UI PASS / SEEK-DEVICE 待测`。

## 6. 对 PR #53 的处置建议

- **不删除**其历史证据；
- 在 PR 审查结论中标注：其 4 例为 `INVALID_FOR_PRODUCT`（框架测试），
  **不得**据此关闭 Seek 验收；
- 本分支的 `PlayerSeekBarContractTest` 为**替代性**有效证据。
