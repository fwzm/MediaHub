## 2026-10-28 05:0x 进度追加（W6-86：监听卡「取消这一次接收」要有账）

### 结论先行

- 改前点「取消这一次接收」，界面上唯一变化是状态跳回「正在监听」。而「正在监听」既是点击前的状态、也是取消后的状态 ⇒ 用户分不清「我取消了」与「点了没反应」。
- 控制器连对端给的原因码都没读：`awaitOnce(cancel)` 的取消分支只做 `_state.value = listeningStateOf(active); return true`，注释写着「本地取消不是失败：不留码」，于是 `TransferFailed.reason` 被丢掉，连 `transfer-cancelled` 都留不下。
- 本轮分工：**失败码口径不动，另立一本账**。取消仍不进 `Failed`、仍无稳定失败码（`codeOf(Listening)` 恒 `null`），但 `Listening` 多两个字段：`cancelledReceives: Int` 与 `lastCancelledReason: String?`。
- 链路：`awaitOnce` 记账 → `listeningStateOf` 带进状态 → `cancelledLineOf(state)` 生成一句人话 → 监听卡在端口行下面渲染一行（tag `sync.listen.cancelled`）。

### 缺的是什么

| 缺口 | 改前的样子 | 后果 |
| --- | --- | --- |
| 状态无处承接取消 | 六个状态里没有「取消过」的空位 | 取消与「什么都没发生」在数据层同形 |
| 原因码被丢掉 | 取消分支不读 `TransferFailed.reason` | 对端因超时/IO 先收手还是用户点的，事后无从分辨 |
| 次数不可观测 | 没有计数器 | 反复取消与点一次取消长得一样 |
| 账会跨场残留（潜在） | 计数挂在控制器上且不清零 | 关监听再开一场，旧账挂到新端口上 |

### 做法（四处）

1. **状态承接**：`Listening` 增 `cancelledReceives: Int = 0` / `lastCancelledReason: String? = null`（默认值 ⇒ 既有构造点零改动）。KDoc 写明为何不另立状态：它没有稳定失败码、也不该让监听停下。
2. **记账与取值优先级**：取消分支 `cancelledReceives++`，然后 `val reason = (outcome as? TransferFailed)?.reason?.trim()?.takeIf { it.isNotEmpty() }`，`lastCancelledReason = reason ?: SourceSyncLocalReasons.CANCELLED`。对端给了码就记对端的，没给才落到本地 `transfer-cancelled`（常量在 `core/common/.../SourceSyncCancellation.kt`）。
3. **一场一账**：`stop()` 在把 `session` 置空后把两个字段一起清零 —— 端口变了、对端也变了，旧账挂新端口比没账更误导。
4. **文案与渲染**：`cancelledLineOf(state)` 非 `Listening` 或计数 ≤ 0 返回 `null`，否则「已取消 N 次等待（最近一次原因：<码>）；取消不是失败，监听仍然开着，可以接着等一次发送。」（码为空时括号段省略）；监听卡在端口行之后插一行 `Text(... testTag = LISTEN_CANCELLED)`，无账时这行不存在。
