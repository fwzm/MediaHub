## 2026-10-25 13:30 进度追加（W6-59：Android 第一个配对入口，只核对链接）

### 为什么是这一片

第 1–10 节把 Android 侧配对**契约**做齐了（载荷 / 帧 / 码 / 挑战 / 指纹 / 链接 / 候选地址 / 回环传输客户端，10 个测试套件），
但 `feature/` 层对这些类**零引用**——契约能解析链接，用户却没有地方贴链接。
目标书 ③「二维码安全配对」在 Android 侧因此等于没有入口。W6-59 补的是入口的第一段。

### 本版边界（写死在界面常量里）

**只核对链接里写明的设备、公钥指纹与剩余有效期，不连接对端。** 四条理由：

| 项 | Windows | Android 本版 |
| --- | --- | --- |
| 回环 TCP 帧交换 | 有 | 有（W6-G） |
| TLS 1.3 + 证书指纹钉扎 | 有 | **没有**（真实拉邀请留 W6-59b） |
| 二维码生成 / 扫码 | 有 | 无相机依赖，不做（只接受粘贴文本） |
| 凭据写入 | 有 | 不做（契约层也没有这类字段） |

「核对成功」绝不显示成「已配好」：结果行末尾固定写「（本版本不连接对端）」。

### 外部可观察语义

- 合法 `mediahub://pair?...` 链接 → 显示设备标识、指纹（16 组 4 字符大写）、剩余秒数、对端 host:port，`codeOf` 为 null。
- 七类失败全部**原样透出 core:common 的契约码**：`pairing-link-empty` / `not-a-pairing-link` / `pairing-link-too-long` / `not-base64url` / `payload-invalid` / `expired`（含版本、字段、URL 类透传）。本层不自造任何 Android 专用码。
- **不泄漏挑战**：`challenge` 不进状态、不进结果行、不进 `toString`；链接原文也不进状态（只留在输入框）。JVM 用例逐字节钉住。
- 上一次成功结论会被下一次失败作废（不留半成品）。

## 2026-10-25 18:33 一节已折叠（W6-61：监听卡「取消这一次接收」—— 取消只结束这次等待，监听仍然开着）

- 缺口：监听卡只有 `stop()` 与 `awaitOnce()`，按下取消没有退路；`close()` 不能当取消（会拆掉整张监听卡并把取消折成 `listener-failed`）。
- 做法：accept 切成 50 ms 短切片（`ACCEPT_SLICE_MS = 50`），每片先看 `cancel?.isCancelled`，到点语义仍是 `transfer-timeout`；连上后 `cancel?.attach(socket)`，`receiveOver` 的 finally `detach`。
- 真缺陷：取消关 socket 后阻塞读抛的 `SocketException` 先被 `SourceSyncTransfer.receive` 折成 `io-failed`，`receiveOver` 的 catch 根本进不去 ⇒ 在 `receive` 的 `is Failed` 分支加统一裁决：取消在任何失败分类之前胜出、只改写失败结果、已收全的信封不被晚到的取消抹掉。
- 本地码沿用 `SourceSyncLocalReasons.CANCELLED = "transfer-cancelled"`，**没有新增任何码**，跨机五集（传输 10 / TLS 4 / 认证 5 / 回执 4 / 投递 1）一字未动。
- 五条外部可观察语义：等 accept 中取消毫秒级回本地码且 `isClosed == false`；阻塞读中取消同样本地码；取消后能再收一封；真 `close()` 仍报 `listener-failed`；界面层取消回 `Listening`（`codeOf == null`）。`cancel == null` 时行为逐字不变。

### 结论先行

- W6-84 让**结果页**会说话了：写失败与永久扣住的条目各自有「下一步」与「复制身份」。但用户真正做决定的地方是**预览页**——那里 `allowable = false` 的条目（凭据、未知类型、内容冲突、历史身份歧义）按钮置灰、只剩一句中文说明，既没说清「点多少次允许都没用」，也没法把身份抄出来去对端处理。
- 预览页的判断依据是 `SourceSyncEntry.candidate.reason`（原因**码**），不是 `blockReason`（那是 `SourceSyncImportLogic.blockReason` 生成的一句中文说明，仅供展示）。W6-84 的 `nextStepOf(withheld: SourceSyncWithheldEntry)` 吃的是结果页的 `reason` 字段，两者语义相同、来源不同。
- 本轮把它拆出唯一出口 `nextStepOfCode(code: String): String?`：结果页、预览页都走同一张表，同一个码在两边**必然**同一句话。表里新增两条码：`same-revision-different-content` 与 `ambiguous-legacy-identity` —— 它们在预览页最常出现，且都属于「本页一律不放行」。
- 「复制身份」在预览页只复制 `candidate.syncSourceId`；身份缺失时键会退化成位置键（`entry-0`、`entry-3`），那种键抄出去对端无从对照 ⇒ 干脆不给按钮。
- 与 Windows 的关系：`SourceSyncImportRound.Preview` 只在信封里找不到记录/带凭据时改 `RequiresApproval` 与原因码，从不提供「下一步」文案或复制动作。Android 这里仍是**超集**，不构成判定分叉——两边对「能不能写」的判断完全一致，多的只是说明与抄写。

### 缺的是什么

| 现象 | 代码位置 | 后果 |
| --- | --- | --- |
| 预览页不可允许条目只有一行 `stateText` | `EntryCard` 的 `if (!entry.allowable)` 块 | 用户不知道下一步该做什么，只能猜 |
| 身份在预览卡片上只是个显示文本 | `entry.key` / `candidate.syncSourceId` | 想拿去对端对照，只能手抄一长串 id |
| 下一步文案只对结果页的 withheld 开放 | `nextStepOf(entry: SourceSyncWithheldEntry)` | 预览页即便想复用也拿不到（类型不同） |
| 冲突/歧义两类码没有任何文案 | `nextStepOfCode` 的 when 表 | 最常见、最需要解释的两类反而静默 |

### 做法（五条）

1. **唯一出口**：`fun nextStepOfCode(code: String): String?` 承接全部判定，`nextStepOf(withheld)` 与新增的 `nextStepOf(entry: SourceSyncEntry)` 都退化成一行委托（`nextStepOfCode(entry.reason)` / `nextStepOfCode(entry.candidate.reason)`）。表内五条已知码，其余（含 `WITHHELD_WITHOUT_REASON`、未知码、空串）返回 null —— 不编建议。
2. **两条新文案**：`SAME_REVISION_DIFFERENT_CONTENT` →「下一步：这条两端内容不一致（版本号相同），本页一律不放行；请在来源页手工对齐后再导出。」；`AMBIGUOUS_LEGACY_IDENTITY` →「下一步：本机有多条来源指向同一身份，先在来源页删掉多余的再重新导出。」
3. **载荷函数**：`fun copyPayloadOf(entry: SourceSyncEntry): String?` 返回 `entry.candidate.syncSourceId?.trim()?.takeIf { it.isNotEmpty() }`。返回 null 就不渲染按钮，页面无需自己判空。
4. **组件复用**：`IdentityCopyButton(identity, tag, onCopyIdentity)`（W6-84 已存在）直接用在 `EntryCard` 里，tag 规则 `SourceSyncImportTags.entryCopy(key)` = `sync.entry.copy:<键>`。下一步文本的 tag 是 `ENTRY_NEXT_STEP` = `sync.entry.nextStep`。
5. **回调链**：`SourceSyncImportScreen` 的 `onCopyIdentity` 参数（W6-84 加的，默认空实现）透传给 `BucketSection` 再透传给 `EntryCard`；route 层的剪贴板注入无需再改。
