# 实施方案：自签名证书信任 + 多版本片源选择

## Context

Windows 端目前可以接入官方 Emby/Jellyfin 并起播，但有两个"什么都支持"原则下的硬缺口：

1. **自签名证书的服务器完全接不进来**。`NetworkPolicyHandlerFactory.CreateHandler` 没有安装任何 TLS 回调，系统默认校验会直接拒绝自签名证书，加服务器在探测阶段就失败，而且用户看不到原因。
2. **多版本片源固定取第一项**。`MediaBrowserProvider.ResolvePlaybackAsync` 取 `MediaSources[0]`，当第一项是"仅转码"（例如 4K 只给 HLS）时会走到一个恒等的死分支，最终要么静默用错源，要么在后续链路里失败且没有可读错误。

拍板结论：**不做全局关闭校验**，改为**每台服务器显式信任其证书指纹（SHA-256 pin）**；加服务器流程必须有明确确认；**任何令牌/密码只能在已校验（系统信任或 pin 匹配）的通道上发送**。

兼容性原则（已记入项目记忆）：目标是"什么都支持、什么都能放"，兼容性优先于体验打磨。

## 一、自签名证书信任

### 1. 新增 `windows/src/MediaHub.Net/CertificateTrust.cs`

| 成员 | 语义 |
| --- | --- |
| `NormalizeFingerprint(string?)` | 去掉 `:`、空格、`-`、`.`，转大写 hex；必须 64 位十六进制，否则返回 `null` |
| `ComputeSha256(X509Certificate?)` | 取 `GetRawCertData()` 的 SHA-256，输出大写 hex |
| `CreateValidationCallback(string pin)` | 返回 `RemoteCertificateValidationCallback`：`errors == SslPolicyErrors.None && cert != null` → `true`；否则仅当叶子证书 SHA-256 与 `pin` 精确匹配（忽略大小写）→ `true`；其余 `false`。回调内**绝不抛异常**（抛异常会中止请求且信息不可用） |
| `PresentedCertificate`（record） | `Host`、`Subject`、`Issuer`、`Sha256`、`NotBefore`、`NotAfter`、`ChainErrors`（`SslPolicyErrors`） |
| `CertificateInspector.InspectAsync(Uri url, TimeSpan timeout, CancellationToken ct)` | 见下 |

`CertificateInspector` 说明（这是"不让令牌走无校验通道"的关键）：

- 仅处理 `https`；`http://` 输入返回 `null`（无 TLS 层可查）。
- `TcpClient` 连 `host:port` → `SslStream`；`RemoteCertificateValidationCallback` 里**记录** `SslPolicyErrors` 与叶子证书后**始终返回 `false`**，让握手按失败结束。因此**不会发出任何 HTTP 请求**，不会有 token/密码进入字节流。
- 若记录的 `errors == None`（系统本来就信任）→ 返回 `null`，表示无需 pin。
- 证书对象用 `X509CertificateLoader.LoadCertificate(raw)` 构造（避免 `new X509Certificate2(byte[])` 的 SYSLIB0057 过时警告）。
- 失败（连接超时/非 TLS/握手异常）→ 返回 `null`，由上层回落到原有"连接失败"消息，不阻塞流程。
- 已知限制（写进文档）：输入是 `http://`、服务器再 302 到自签名 `https://` 的场景，Inspector 基于输入 scheme 判断，不会提示。此情况先在文档记录，不改探测流程。

### 2. `windows/src/MediaHub.Net/NetworkPolicy.cs`

- 新增 `public string? TrustedCertificateSha256 { get; init; }`（默认为 `null`，只影响当前源的 handler）。
- `Validate()`：非空时 `NormalizeFingerprint` 必须成功，否则抛 `ArgumentException`（明确提示 pin 需为 64 位 SHA-256）。
- `Describe()` 追加证书信任状态（供诊断面板/日志）。
- `NetworkPolicyHandlerFactory.CreateHandler`：规范化 pin 后若存在，设置
  `handler.SslOptions.RemoteCertificateValidationCallback = CertificateTrust.CreateValidationCallback(pin);`
  未设置时**完全不触碰** `SslOptions`，保持系统默认校验。
- 影响面自动覆盖该源的全部请求（API / 图片 / 字幕 / 播放流 / 心跳），因为 `MediaSourceHttpClientFactory` 的两个 handler 都来自这个工厂。
- 注释中说明：pin 匹配即通过意味着**不再校验主机名与链**（自签证书常见 CN/SAN 不匹配），这是刻意的——pin 已把信任收敛到唯一一张证书；且作用域仅该源。

### 3. 持久化与统一取策略

| 文件 | 改动 |
| --- | --- |
| `windows/src/MediaHub.App/Services/SettingsStore.cs` | `PersistedServer` 增加 `public string? TrustedCertificateSha256 { get; set; }`（JSON 缺省为 `null`，旧配置文件向后兼容） |
| `windows/src/MediaHub.App/Services/ServerManager.cs` | `ServerEntry` 增加同名字段；新增 `PolicyFor(ServerEntry entry)` → `NetworkPolicy.FollowSystem with { TrustedCertificateSha256 = entry.TrustedCertificateSha256 }`；`InitializeAsync` 从 `PersistedServer` 恢复该字段；`RestoreAsync` / `ReconnectAsync` / `RetestAsync` 一律用 `PolicyFor(entry)` 建句柄与探测（替换写死的 `NetworkPolicy.FollowSystem`）；`PersistAsync` 写入 pin |

### 4. 加服务器流程的明确确认（UI）

`ServerManager`：

- 新增 `sealed record ServerAddResult(bool Ok, string Message, PresentedCertificate? UntrustedCertificate)`。
- `AddAsync(...)`：探测失败且输入是 `https://` 时调 `CertificateInspector.InspectAsync`；拿到证书则返回 `Ok=false` + `UntrustedCertificate=cert`，消息说明"服务器使用了本机不信任的证书，需要确认后才能继续"。
- **顺序保证**：第一次 `AddAsync`（无 pin）在 TLS 握手阶段就失败，**不会发送用户名/密码**；只有第二次带 pin 的调用才可能把凭据发出去。

`windows/src/MediaHub.App/Views/SourcesPage.xaml.cs`：

- `testButton.Click`：失败时调 `InspectAsync`，把 `Subject / Issuer / 有效期 / SHA-256` 写进 `hint`（不弹嵌套 `ContentDialog`），提示"添加时会要求确认信任"。
- `OnAddClick`：`dialog.ShowAsync()` 返回 Primary 后执行 `AddAsync`；若 `UntrustedCertificate != null`，**再弹一个** `ContentDialog`：
  - 标题："信任该服务器的证书？"
  - 内容：Host、Subject、Issuer、有效期、SHA-256（等宽显示），加一句"仅为该服务器保存此指纹，不会关闭全局证书校验。若服务器更换证书，需要重新确认。"
  - `PrimaryButtonText = "信任并继续登录"`，`CloseButtonText = "取消"`，默认按钮为 Close（避免误触）。
  - 确认 → `AddAsync(..., policy with { TrustedCertificateSha256 = cert.Sha256 })`，成功则把 pin 写入 entry/persisted；取消 → 不加服务器、不保存 pin。

## 二、多版本片源选择

`windows/src/MediaHub.Providers/MediaBrowser/MediaBrowserProvider.cs` 的 `ResolvePlaybackAsync`：

1. 从 `PlaybackInfo.MediaSources` 中过滤出**可本地播放**的源：`GetBool(SupportsDirectPlay) != false || GetBool(SupportsDirectStream) != false`。
2. 优先选第一个 `SupportsDirectPlay != false`；没有则选第一个 `SupportsDirectStream != false`。
3. 删除现有恒等三元分支（`supportsDirectStream ? DirectStreamUrl(...) : DirectStreamUrl(...)`）。
4. 按选择设置 `PlaybackMode`：直放 → `DirectPlay`，直串流 → `Stream`；保留 `RunTimeTicks`、`Streams`、`Id` 等原有字段。
5. **全部为仅转码**（过滤后为空且原始列表非空）→
   `throw ProviderException.Connection(_serverId, "该片源只提供转码流，当前版本不支持转码播放")`。
6. 原始 `MediaSources` 为空 → 保持现有错误路径（`NotFound`/`Parse`），不做行为变更。

不改 `PlaybackSource` 契约、不加"让用户手选版本"的 UI（本轮只需要"能选到能放的源 + 明确失败"，手选版本留到后续）。

## 三、测试与文档

新增/修改测试（`windows/tests/MediaHub.Tests`）：

- `CertificateTrustTests.cs`：`NormalizeFingerprint` 正反例（带冒号/小写/空格 → 规范化；63 位、含非 hex → `null`）；`CreateValidationCallback` 的三条分支（系统信任通过、正确 pin 通过、错误 pin 拒绝）。
- 本地 TLS 测试：`CertificateRequest` 生成自签证书 + `TcpListener`/`SslStream` 起一个只做握手的监听，验证
  - 用该证书挂 `NetworkPolicy.TrustedCertificateSha256` 的 handler 能完成请求；
  - 不挂 pin 时请求失败；
  - `CertificateInspector.InspectAsync` 返回的 SHA-256 与证书一致，且服务端**没有收到任何 HTTP 请求字节**。
- `MockServerIntegrationTests.cs` 增加：`MediaSources = [仅转码, 可直放]` → 选中第二项且 `Mode == DirectPlay`；`MediaSources = [仅转码, 仅转码]` → 抛 `ProviderErrorCode.Connection` 且消息含"只提供转码流"。
  （若 `MockMediaServer` 的 PlaybackInfo 是写死的，给它加一个可注入的 `MediaSources` 覆盖开关，仅在测试里使用。）

文档：

- `windows/docs/CAPABILITY-MAP.md` 增加两行：
  - `自签名证书（按服务器证书指纹信任）| IMPLEMENTED_UNVERIFIED`
  - `多版本片源选择（跳过仅转码源）| IMPLEMENTED_UNVERIFIED`
- 在 `windows/docs/DECISIONS.md` 追加一条决策：per-server SHA-256 pin，不提供"关闭证书校验"全局开关；令牌只在系统信任或 pin 匹配后发送；已知限制（http→https 重定向不提示）。

### 验证

```powershell
dotnet build windows/src/MediaHub.App/MediaHub.App.csproj -c Debug -p:Platform=x64
dotnet test  windows/tests/MediaHub.Tests/MediaHub.Tests.csproj -c Debug -p:Platform=x64
```

手工验收（本机自签 HTTPS 服务，例如 `dotnet dev-certs` 或 openssl 生成的自签证书）：

1. 添加该服务器 → 应看到"本机不信任的证书"提示 + 指纹；
2. 点"信任并继续登录" → 能登录成功，凭据库写入；
3. 重启应用 → 服务器仍是已连接（pin 已持久化）；
4. 用另一个指纹（改证书）→ 恢复失败，回落到"需要确认"，不会静默放行；
5. 取消确认 → 不新增服务器、不写 pin。

## 四、转码 / HLS 评估（只出结论，不实现）

两项完成后单独形成结论：必要性（仅转码源、HEVC/AV1 不在本机能力内、容器不支持时的兜底）、工作量（Emby `PlaybackInfo` 带 `DeviceProfile` 请求转码流、HLS 直连 vs 本地代理、进度/心跳按转码会话上报、mpv `hls` 支持与 `--hls-bitrate`）、以及代价（服务端 CPU/带宽、seek 与字幕时序、错误面变大、测试矩阵膨胀）。以最终回复形式给出，不写入本轮代码。

不在本轮范围：真正的转码/HLS 播放、手选片源版本 UI、`SourceRegistry.cs`（全仓无引用的死代码）清理。
